# Relay — repository conventions

Relay is an organisational continuity SaaS. Decisions live in `docs/blueprint/`
(Decision Register = D1–D26, Implementation Plan = milestones). Read the relevant
section there; don't re-derive decisions. Record any deviation as an ADR in `docs/adr/`.

## Layout
- `backend/` — Python 3.14, FastAPI, SQLAlchemy 2.x async, psycopg 3, Alembic. `uv`.
  - `src/relay/<module>/` — one package per domain module; `src/relay/shared/` for cross-cutting code.
  - `migrations/versions/` — hand-written, numbered `NNNN_slug.py`.
  - `tests/` — real PostgreSQL only (never SQLite).
- `frontend/` — Next.js (App Router), TypeScript, Tailwind, shadcn/ui. `pnpm`.
  Read `frontend/AGENTS.md`: this Next.js version differs from older training data.
- `infra/db/init/` — local/CI role provisioning. `docker-compose.yml` — local Postgres.

## Commands
- DB: `docker compose up -d --wait`
- Backend (in `backend/`): `uv run alembic upgrade head` · `uv run relay-api` · `uv run relay-worker` ·
  `uv run pytest` · `uv run ruff format . && uv run ruff check .` · `uv run mypy`
- Frontend (in `frontend/`): `pnpm dev` · `pnpm lint` · `pnpm typecheck` · `pnpm format` · `pnpm build`

## Non-negotiable guardrails
1. Identity comes only from a verified WorkOS access token (`Identity` dependency). Tenant
   comes only from an active Relay membership (`CurrentWorkspace` dependency), never from
   client input. Authentication, membership resolution and authorization stay separate.
2. Tenant data is accessed only through `unit_of_work(factory, tenant_id, principal)`; it
   applies `set_config('app.tenant_id' / 'app.principal', …, true)` per transaction. HTTP
   handlers get tenant sessions from `CurrentWorkspace` only. Never use session-level `SET`.
   Raw `engine.connect()` is for non-tenant operations only (e.g. readiness).
3. Every tenant table: `tenant_id NOT NULL`, `UNIQUE (tenant_id, id)`, all other unique keys
   start with `tenant_id`, references are composite `(tenant_id, x_id)` FKs, and
   `enable_tenant_rls()` in its migration (ENABLE + FORCE + fail-closed policy).
   `tests/security/test_schema_conventions.py` enforces this.
4. The app connects as `relay_app` (no superuser, no BYPASSRLS, owns nothing). Migrations run
   as the owner role. Grant privileges explicitly per table in migrations.
5. Migrations are hand-written: RLS, grants, functions and EXCLUDE constraints are not
   autogenerated. Models must match migrations (drift test). Expand/contract; no drop+rename
   in the same release as the code change.
6. One `AsyncSession` per request/job; never share across concurrent tasks; no lazy loading
   in async paths.
7. Pydantic DTOs are separate from ORM models; Python is the only backend (no business logic
   in Next.js).
8. No Redis, Celery, Temporal, LangGraph, Neo4j, Qdrant, brokers or microservices without an
   ADR showing a Register trigger was met. Queue = Procrastinate behind a transactional outbox.
9. LLMs (later milestones) only produce proposals; they never hold write tools.
10. No AGPL/GPL/SSPL/BSL/SUL production dependencies.
11. Every service that reads or changes protected data calls `authorize()` (and lists use
    `visible()`) from `relay/policy/permissions.py` *inside the service*. New permissions are
    registry entries; unknown permissions and roles are denied.
12. Audit events (`relay/audit/service.record`) are written in the same transaction as the
    change; the table is append-only. Metadata holds identifiers/enums only, never tokens,
    secrets or user content.
13. Domain events go through `relay/jobs/outbox.emit` in the domain transaction; it defers the
    Procrastinate job on the same connection. Handlers must be idempotent and run under the
    job's tenant context as `relay_app`. Procrastinate's schema is vendored per version
    (`migrations/sql/`); upgrading it needs a migration.

## Naming and code conventions
- Backend request bodies: `<Thing>In` / `<Thing>Update`, subclassing `StrictInput` (unknown fields
  rejected). Responses: `<Thing>View` (list rows may be `<Thing>Summary`, full records `<Thing>Detail`).
- Services: `relay/<module>/service.py` (verb-first: `create_x`, `list_x`, `update_x`); thin
  routers in `relay/<module>/api.py`; ORM models in `models.py`. No raw SQL strings in application
  code: use SQLAlchemy expressions (`select`, `func.*`). Raw DDL belongs only in migrations.
- Frontend types in `src/lib/types.ts` mirror backend `*View` names and snake_case fields exactly.
  Server actions are `<verb><Thing>Action`; API calls go through `api.*` in `src/lib/relay-api.ts`.
- Timestamps are timezone-aware ISO 8601 (`AwareDatetime`); ranges are half-open `[from, to)`.

## Windows note
psycopg async needs a selector event loop on Windows; `relay/__main__.py`, `migrations/env.py`
and `tests/conftest.py` already handle it. Start the API with `uv run relay-api`, not bare
`uvicorn`.
