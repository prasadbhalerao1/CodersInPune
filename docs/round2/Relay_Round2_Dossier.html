Relay

Accountability that transfers, with proof

When someone who owns critical operational responsibilities leaves, goes on leave, or transfers projects, the knowledge does not leave in one piece. It is scattered across repositories, issue trackers, documents, and individual heads. Relay builds an authoritative live map of who is accountable for what, detects continuity risks before they cause outages, ingests verified evidence across GitHub, Linear, and Notion, and conducts handovers as governed, audited cases with provable readiness.

1Understanding the problem and solution

Every growing team hits the same crisis: someone who "just knew how everything worked" leaves or becomes unavailable. The codebase stays in GitHub, tickets sit in Linear, runbooks reside in Notion, but the operational context, unwritten edge cases, and active accountability disappear. The incoming owner spends their first months guessing, while managers discover unowned services only after a customer-facing outage.

1.1 The three core product promises

  • 1. Understand the organisation: Establish a live map of people, teams, departments, responsibilities, and assets. Track who is accountable as primary, backup, or co-owner with an immutable history.
  • 2. Keep work moving: Ingest read-only operational signals across GitHub, Linear, and Notion. Identify continuity risks (no backup, single-point-of-failure, stale knowledge, unowned assets) and calculate a live Continuity Debt score.
  • 3. Verify the transfer: Coordinate handovers through structured continuity cases. The AI drafts evidence-backed findings and proposals; human managers review and accept them; and the incoming owner acknowledges a specific, immutable version.

2Architecture and request data flow

Relay is engineered as a resilient modular monolith. All business logic, tenancy enforcement, and policy evaluations live in Python. Next.js 16 acts purely as a presentation layer using Server Components and Server Actions, passing the verified WorkOS bearer token down to FastAPI.

2.1 Database-enforced multitenancy

Unlike conventional multi-tenant apps that rely solely on application-level filtering (e.g. WHERE tenant_id = ?), Relay enforces isolation in the database engine itself:

  • Forced Row-Level Security: ALTER TABLE ... FORCE ROW LEVEL SECURITY is applied across all 84 tenant tables. Table owners cannot bypass RLS.
  • Restricted App Role: The API connects as relay_app, which owns zero schema, has no SUPERUSER or BYPASSRLS rights, and holds zero DELETE privileges on audit tables.
  • Transaction-Scoped Context: Every API request establishes tenant context via SELECT set_config('app.tenant_id', :id, true). Because the third parameter is true, the configuration automatically clears when the transaction commits, preventing connection pool context bleed.

3.1 Source permission and audience boundary

Relay never assumes all workspace members should see every connected resource. Every imported repository, project, and document carries an explicit audience:

  • Private Repositories & Linear Projects: Automatically default to managers only upon sync.
  • Audited Widening: An admin can widen an audience to workspace, but this action is recorded permanently in the audit log.
  • Automatic Re-narrowing: If a repository is changed from public to private on GitHub, Relay automatically re-narrows its audience back to managers on the next webhook delivery.
  • Inherited Context: AI claims and context capsules inherit the narrowest audience among their cited sources. A non-manager viewing a capsule will never see citations or summaries derived from manager-only sources.

4Governed AI pipeline & evaluation

Relay treats LLMs as drafting engines, never as autonomous decision-makers. AI models operate inside an untrusted-content envelope with read-only tools and produce proposals only. No model can alter ownership, reassign tasks, or change system state.

5.1 Distributed rate limiting without Redis

To support multi-replica horizontal scaling without introducing an external Redis cluster, rate limits are implemented directly in PostgreSQL via a SECURITY DEFINER function (migration 0038). Atomic token-bucket counters are updated per-tenant and per-action (e.g. login, OAuth start, AI analysis, sync) in single atomic queries. The restricted relay_app role can execute the check function but cannot tamper with counter rows.

6.1 Immutable transaction-coupled audit trail

Audit events commit within the exact same database transaction as domain changes. A PostgreSQL table trigger strictly forbids UPDATE or DELETE operations on audit records, ensuring that neither an API vulnerability nor a compromised application process can erase historical records.

7What changed from Round 1 and why

Relay expanded significantly from the initial Round 1 concept to solve the real operational bottlenecks discovered during development:

AreaRound 1 ProposalRound 2 Implemented Reality & Justification
Product Scope Single-tool engineering offboarding centered solely on GitHub. Multi-source organisational continuity: Connects GitHub (code/PRs), Linear (issues/cycles), and Notion (runbooks) into unified continuity graphs across departments.
Infrastructure Stack External Redis queue and planned vector database. PostgreSQL-native architecture: Procrastinate transactional outbox, PostgreSQL full-text search, and atomic SECURITY DEFINER rate limiting eliminate split-brain risks and zero-cost hosting feasibility.
AI Governance Autonomous agent actions creating tasks directly. Proposal-only agency: AI operates with read-only tools in an untrusted sandbox; every proposal waits in a tray for human manager approval.
Notion Integration Unrestricted workspace document ingestion. Fail-closed admin mapping: Discovers page hierarchy but only imports pages explicitly mapped to a responsibility, tracking SHA-256 revision hashes.
Handover Format Downloadable static PDF and Markdown files. Per-viewer dynamic context capsules: Re-evaluated on every render to enforce live permissions, with explicit omissions reporting for unauthorized items.

8Three deliverable improvements for Round 3

Each improvement builds on parts that already work in Round 2: the cited AI pipeline, the risk engine, ownership history and the GitHub, Linear and Notion connectors. Full scope and acceptance criteria are in docs/improvements.md.

1. AI Handover Copilot

What it is: When a responsibility transfers, Relay generates a case-specific Handover Brief from the responsibility, ownership history, connected GitHub, Linear and Notion evidence, knowledge, open work and existing risks. It highlights what the incoming owner must know, missing or conflicting information, important changes and recommended handover tasks, each with supporting evidence.

User impact: The incoming owner can ask questions about the handover and gets answers grounded only in the authorised evidence attached to that case. If the evidence does not cover a question, the answer says so.

2. "What If?" Continuity Simulator

What it is: A simulation mode for testing what happens if a key person becomes unavailable. A manager selects a person and sees the affected responsibilities, assets, risks, open work, knowledge gaps and single-person dependencies.

User impact: The manager picks a possible backup or temporary owner and previews the resulting coverage and remaining risks, without changing any real ownership records. Readiness is tested before an absence or departure happens.

3. Project Memory Replay

What it is: An interactive timeline that reconstructs how a project evolved. Commits, pull requests, issues and linked documentation are grouped into events such as major implementations, technical changes, bug fixes, incidents and documentation updates. AI explains what happened, why it matters and how events connect, with source links and clear uncertainty labels.

User impact: Incoming owners browse the project chronologically, filter by category, play back its evolution and inspect the evidence behind each event. They learn how the project reached its current state, not only what it is today.

9Pilot limitations and honest assessment

Relay adheres to strict truth-in-advertising. We openly document current operational boundaries:

  • Render Free-Tier Spin-Down: The free API instance spins down after 15 minutes of inactivity. First requests experience a 30-50s wake-up delay. This is actively mitigated by our 10-minute automated GitHub Actions monitor.
  • Transactional Email Provider: Render free hosting blocks outbound SMTP. Live email delivery requires configuring a verified third-party provider (such as Resend).
  • Gemini Free-Tier Privacy Notice: Current API keys use Google's free tier. While the application code prevents data leaks, production customer deployments must move to a paid Google Cloud agreement for enterprise zero-training guarantees.
  • Per-User Source ACL Mirroring: Private repos fail closed (managers-only). Dynamic per-user mirroring of individual GitHub/Notion ACLs is on the roadmap after Round 3.
